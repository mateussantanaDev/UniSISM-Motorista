UNISISM MOTORISTA

DOCUMENTAÇÃO TÉCNICA · v0.1.0 · 2026-05

App mobile Flutter da face Motorista do ecossistema UNISISM. Atende motoristas do transporte sanitário TFD (Tratamento Fora do Domicílio) da Prefeitura Municipal contratante. Ver escala do dia, fazer chamada digital dos pacientes, registrar hodômetro, solicitar abastecimento e ajuda de custo — offline-first, com sincronização automática quando a rede volta.

FACE MOTORISTA — ECOSSISTEMA UNISISM

Faces irmãs:

  • Face UBS — SvelteKit em unisism-ubs/frontend (existente)
  • Face SMS / Regulação — a construir (Face 2)
  • Face Paciente — outro app Flutter em unisism-ubs/backend/docs/flutter/
  • Face Motorista — este projeto

A identidade visual partiu do Design System B2G Brutalista da Face UBS, mas foi refatorada em 2026-05-25 para um perfil mais acessível — motoristas têm leitura básica e operam o app no celular com pouco tempo. Cores e cantos retos do UNISISM continuam; tipografia, botões e linguagem foram humanizados.

01VISÃO GERAL

O que o app faz (MVP, pós-simplificação)

  • Login via matrícula funcional + senha (com troca obrigatória no 1º acesso).
  • Lista de viagens em três abas: Hoje · Próximas · Histórico.
  • Detalhe da viagem com passageiros, veículo, quilometragem e mapa offline.
  • Chamada digital com botões grandes: "Embarcou ✓" / "Faltou ✗" / "Mais" pra cada paciente.
  • Quilometragem: começar viagem (KM antes) e finalizar (KM agora).
  • Mapa offline (OpenStreetMap): pontos de origem, destino e UBSs dos passageiros.
  • Visualização da ajuda de custo alocada a cada paciente da viagem.
  • Perfil do motorista (CNH com aviso de vencimento, total de viagens, KM rodados).
  • Push notifications (FCM) — infraestrutura pronta, ativação manual.
REMOVIDO POR FEEDBACK DO USUÁRIO

Abastecimento (originalmente F12) — funcionalidade considerada não-essencial pro caso de uso primário. Tudo foi desfeito (telas, repository, modelo, rotas, deps órfãs image_picker e permission_handler). Bottom nav voltou a ter 2 abas.

REFATORAÇÃO DE ACESSIBILIDADE — 2026-05-25

O Design System foi simplificado pra atender motoristas com leitura básica. Principais mudanças:

  • Tipografia maior: body 14→16px, label 10→12px, métrica 30→36px.
  • Sans-serif (Inter) é o padrão; mono só pra dados (CPF, hora, KM).
  • Sem uppercase agressivo: "Iniciar viagem" no lugar de "INICIAR VIAGEM".
  • Botões 56dp+ (área de toque ideal).
  • Linguagem coloquial: "Sair do app" no lugar de "Encerrar sessão"; "Quilometragem antes de sair" no lugar de "Hodômetro inicial".
  • SyncIndicator humanizado: "Tudo salvo" / "Sem internet" / "Enviando…" no lugar de "SINCRONIZADO" / "OFFLINE · 4 PENDENTES".
  • StatusBadge com ícone e palavras simples: "Embarcou" no lugar de "EMBARCADO".
  • ViagemCard com hora grande (22px mono) em destaque.
  • Bottom nav com ícones 28dp e labels sans-serif.
  • Chamada digital sem swipe oculto: dois botões grandes "Embarcou ✓" / "Faltou ✗" + botão "Mais" abrindo bottom sheet.
  • Numeração decorativa "01/02/03" dos painéis removida.

O brutalismo B2G original da Face UBS continua intacto — essa simplificação é exclusiva do app do motorista, que tem perfil diferente do gestor TFD.

Diferencial: offline-first com auditoria preservada

O motorista frequentemente opera em áreas com sinal instável (BR-101, interior, rodoviárias). O app foi desenhado para que toda ação funcione offline — a chamada digital, marcar hodômetro, anexar foto, tudo é gravado localmente e enfileirado em uma outbox. Quando a rede volta, o sync engine drena a outbox para o backend, preservando a ordem das operações e respeitando a cadeia de auditoria criptográfica TJ.

Princípios da stack

  • Sem code-gen pesado — apenas Drift usa build_runner. Sem freezed, json_serializable, retrofit. Modelos têm fromJson/toJson manuais.
  • Sem state-management mágico — Riverpod 2 com Notifier/Provider/StreamProvider; sem code-gen do riverpod_generator.

  • Sem Google Maps — escolha deliberada de OpenStreetMap por gratuidade e suporte offline-first.

Estratégia de armazenamento — colunas tipadas + rawJson

Cada linha tem campos críticos como colunas tipadas (para query/index) e um rawJson com o objeto inteiro serializado. Isso permite:

  • Queries rápidas em data, status, presenca
  • Reidratação completa do modelo de domínio (com observações de mobilidade, coordenadas, telefone, etc.) sem alterar o schema toda vez que o backend adiciona campo

Flag dirty

Toda mutação local marca a linha (viagens ou passageiros) com dirty = true. O upsert vindo de um pull preserva linhas dirty — o sync engine reconcilia via outbox. Quando o POST correspondente chega ao servidor, o OutboxProcessor chama clearDirty* e o estado converge.

PENDENTE NO BACKEND

O módulo /motorista-app/* ainda não existe no backend unisism-ubs/backend. A spec exata de rotas, schema (vincular MotoristaTFD.usuarioId), role nova (MOTORISTA_TFD) e payloads está em BACKEND_REQUIREMENTS.md. Estimativa: 3-5 dias.

Tratamento de erros

Toda falha é normalizada em ApiException com:

  • code — semântico (ex.: CNH_VENCIDA, HODOMETRO_INVALIDO, OFFLINE)
  • message — texto user-facing
  • status — HTTP code (nullable para erros locais)
  • details — payload extra do backend

Helpers: isOffline, isUnauthorized, isConflict, isValidation.

10SYNC ENGINE

Orquestra pull (servidor → DB local) e push (outbox → servidor). Reage a:

  • Mudança de conectividade (volta a online → sync imediato)
  • Timer periódico (5 minutos)
  • Login bem-sucedido
  • Pull-to-refresh manual da UI

Snapshot reativo

class SyncSnapshot {
  SyncRunState state;   // idle | syncing | error
  bool online;
  int pendingCount;     // linhas PENDING/RETRYING na outbox
  DateTime? lastSyncAt; // vem do header X-Server-Time
  String? lastError;
}

A UI consome via syncStatusProvider e renderiza no SyncIndicator do header.

Outbox: ciclo de vida

┌────────────────────────────────────────────────────────────┐ │ marcar passageiro AUSENTE (offline) │ │ ↓ │ │ ViagensRepository.marcarPresenca() │ │ ├─ ViagensDao.setPresencaLocal() → DB local + dirty=1 │ │ └─ OutboxDao.enqueue() → status=PENDING │ │ ↓ │ │ UI atualiza imediatamente (escrita otimista) │ │ ↓ │ │ ... [tempo depois] connectivity online ... │ │ ↓ │ │ SyncEngine.setOnline(true) → syncAll() │ │ 1. OutboxProcessor.drain() │ │ ├─ pega rows PENDING/RETRYING │ │ ├─ dispatch por entityKind → TfdApi.marcarPresenca() │ │ ├─ on success: markDone + clearDirtyPassageiro │ │ ├─ on 409: markFailed(conflict=true) → UI manual │ │ ├─ on 5xx/offline: markRetrying (até 5 tentativas) │ │ └─ on 4xx permanente: markFailed │ │ 2. pull() — GET /minhas-viagens?desde=lastSyncAt │ │ ├─ upsert viagens (preservando dirty) │ │ └─ atualiza lastSyncAt com X-Server-Time │ └────────────────────────────────────────────────────────────┘

OutboxKinds (dispatcher)

  • INICIAR_VIAGEM
  • CONCLUIR_VIAGEM
  • MARCAR_PRESENCA
  • SOLICITAR_ABASTECIMENTO
  • ANEXAR_COMPROVANTE
  • REGISTRAR_FCM

Retry com backoff

Até 5 tentativas com espera exponencial (2^n segundos). Após o limite, status vira FAILED e exige intervenção manual (UI de conflitos vem em fase futura).

Restoração de sessão

  1. App abre → splash mostra (status = restoring)
  2. SecureTokenStorage lê token do flutter_secure_storage
  3. Se token existe, tenta api.me():
  4. ↳ ok → loggedIn + cache do motorista local
  5. ↳ 401 → limpa storage → loggedOut
  6. ↳ offline (sem rede) → loggedIn com dados em cache
  7. Se sem token → loggedOut

15BACKEND — O QUE FALTA

SPEC EM BACKEND_REQUIREMENTS.md

O backend unisism-ubs/backend já tem o modelo TFD completo (MotoristaTFD, VeiculoTFD, ViagemFrota, ViagemPassageiro) e endpoints /v1/tfd/* para uso do GESTOR_TFD. O que falta é o módulo paralelo /motorista-app/*, análogo ao /paciente-app/*, com auth próprio.

Resumo do que precisa

  1. Schema Prisma:
    • Adicionar MotoristaTFD.usuarioId + primeiroLogin + fcmToken
    • Enum Role ganha MOTORISTA_TFD
    • Migration + backfill (criar Usuario para motoristas existentes)
  2. Módulo src/modules/motorista-app/ com 13 rotas:
    • 4 de auth (login, trocar-senha, logout, me)
    • 5 de viagens (listar minhas, detalhe, iniciar, concluir, presença)
    • 3 de abastecimento (criar, anexar, listar minhas)
    • 1 de ajudas de custo (listar)
    • 2 de FCM (registrar/revogar token)
  3. Middleware de auth que injeta motoristaId + filtra por ele.
  4. Header X-Server-Time em todos os GET.
  5. Auditoria tfd_audit_log usando motorista.usuarioId.
  6. Testes integrados cobrindo o golden path.

Estimativa: 3-5 dias para um dev backend que já conhece o módulo paciente-app (pattern idêntico).

16DECISÕES TÉCNICAS

#DecisãoPor quê
D1 Frontend primeiro, backend depois Acelerou entrega visual; TfdApiMock espelhava o contrato exato. Removido após o backend ser implementado (2026-05-26) — app agora consome só dados reais.
D2 Auth via matrícula + senha (não SSO) Padrão do servidor público brasileiro. Provisória + troca obrigatória no 1º login.
D3 Drift (SQLite) sobre Hive Tipagem forte, queries SQL puras, migrations explícitas, suporte a watch streams reativos.
D4 Outbox table sobre fila em memória Sobrevive a crash + restart. Garante at-least-once mesmo com app forçado a fechar.
D5 Escrita otimista (UI atualiza antes do servidor) UX percebida — chamada digital tem que parecer instantânea mesmo offline.
D6 OpenStreetMap sobre Google Maps Gratuito, offline-friendly, sem chave de API, sem custo recorrente da PMFS.
D7 Inter + JetBrains Mono empacotadas LGPD/air-gap — sem fetch de CDN do Google Fonts em runtime.
D8 Sem freezed/json_serializable Reduz build time, dependências e código gerado. Manual fromJson é OK para o tamanho do projeto.
D9 Riverpod 2 (não 3) API estável, sem code-gen obrigatório.
D10 Coluna rawJson nas tabelas Adia decisões de schema quando o backend evolui. Campos críticos ficam indexados; resto é JSON.
